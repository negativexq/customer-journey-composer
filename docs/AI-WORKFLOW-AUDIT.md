# AI workflow acceptance audit — 2026-11-11

Audited revision: `1da5339`. Scope: the recorded Luna recovery proposal, its ten
customer/event scenarios, AI producer contract, graph/message validation,
publication gate, simulator/runtime parity and generation accounting. This is a
focused correctness audit, not a dependency/security scan or general model eval.
No new model generation, publish, real send, benchmark or deployment was run.
Application behavior was not modified.

## Findings, in priority order

### P1 — Publication readiness ignores known acceptance failures

`apps/api/internal/httpapi/publish.go:35` checks only whether **any** finalized
FULL run with the same workspace/journey/workflow hash passed. It does not
consult failing scenarios or a required acceptance suite. This is not a stale
workflow/hash or tenant-isolation issue: all the reproduced runs use the exact
same workflow. The publish POST calls this same function inside its transaction
(`workflows.go:86`), and the UI treats absence of `test_required` as a passing
full-test gate (`PublishReview.vue:36`).

A local GET-only probe reproduced:

- Before tests: `ready=false`, issue `test_required`.
- After the ten scenarios: generated 4 PASS / 6 FAIL, reference 10 PASS / 0 FAIL.
- For the generated draft, `publish-check` then returns `ready=true`, `issues=[]`.

[Raw proof](validation/luna-audit-publish-check.json). Actual publication was not
called; both drafts still have zero versions and live executions/deliveries.
Admin approval is still required; this is an insufficient release-quality gate,
not automatic AI publication or an authorization bypass.

**Impact:** a known-bad journey can pass the pre-launch readiness screen as soon
as one easier scenario passes. An under-threshold cart can pass without ever
exercising message nodes. Current readiness proves only a smoke test exists,
not that the required customer journeys passed.

**Fix direction:** define required scenarios for the workflow/brief and require
the latest applicable result for each to pass for the exact workflow and
scenario revision. Surface missing/failing cases in pre-launch review. Do not
reject every historical failure forever: a corrected scenario must be rerunnable,
and optional exploratory failures need an explicit policy. Add deterministic
mixed PASS/FAIL, missing-case, stale-hash and rerun coverage; no paid model needed.

### P1 — AI acceptance verifies structure, not the requested behavior

`ai/composer.go:167` accepts the normalized candidate after
`messaging.ValidateWorkflow`. That function (`messaging/validate.go:8`) checks
graph/configuration and renderability. The AI input/proposal has a free-text
prompt and workflow (`ai/composer.go:19`, `:39`), with no machine-readable
requirement set against which omitted decisions can be checked. The repair loop
receives structural validation issues, so a valid graph with missing business
checks is accepted without repair.

The recorded flow has no condition reading `customer.attributes.cart_purchased`.
Its global exit is driven by `purchase_completed` events. The canonical control
explicitly has the initial and final profile checks (`catalog/recovery_eur.go:21`,
`:28`). Scenarios I/J prove the consequence: the generated flow sends two
messages for an already-purchased cart and misses the final profile-only purchase
update. Both canonical runs pass with the identical scenarios.

The review UI shows entry event, node count, global exit and re-entry
(`AIPanel.vue:201`) but cannot flag omitted brief requirements; its warnings are
also generated by the model. Human review remains necessary, but a generic
warning checkbox cannot substitute for explicit requirement coverage.

**Fix direction:** expose a small, user-reviewed structured plan/acceptance
contract for the supported journey, then validate/simulate its required behaviors
before marking the proposal ready. Surface unmet/unknown criteria instead of
claiming graph validity means brief compliance. Do not hardcode cart-specific
profile fields into the universal runtime or rely on a stronger model alone.

### P1 — Human-facing exit labels double as machine outcome codes

The AI schema permits any string in `exit.reason` (`ai/schema.go:63`). The graph
validator requires only a nonempty reason (`workflow/workflow.go:182`), while
runtime normal completion requires the exact value `completed`
(`runtime/worker.go:342`); simulator uses the same mapping
(`simulation/nodes.go:101`). Every other reason becomes EXITED.

Our live test brief used the ambiguous human phrase `completed/non-converted`.
The model copied it literally and used another free-text reason for no SMS
consent. Consequently C/D/G have correct message counts but fail terminal-state
or outcome assertions. The prompt authoring ambiguity is part of the failure;
this is not solely a model mistake. AI producer and runtime agree on JSON shape
but not on the semantic outcome vocabulary.

**Impact:** custom text that sounds like normal completion is counted as EXITED
rather than COMPLETED; downstream completion analytics would reflect that state.
No production analytics were changed during these sandbox checks.

**Fix direction:** constrain newly AI-proposed outcome codes and document their
meaning in the system prompt, with separate human-readable descriptions. Preserve
intentional manual custom exits. Do not infer completion from string prefixes,
translate arbitrary prose in the worker, or reinterpret immutable versions.

### P2 — No-channel customers take a 25-hour path instead of immediate exit

The generated trigger goes directly to its one-hour wait. It checks email
consent afterward, then waits 24 hours before checking SMS consent. There is no
initial "any permitted channel" decision. Scenario H produces no messages but
exits at +90,000 seconds rather than +0 seconds. The canonical entry gate
(`catalog/recovery_eur.go:19`) exits immediately and passes the same test.

**Impact:** incorrect behavior and avoidable active/waiting executions for this
brief. This is **not** evidence of sending without consent: shared delivery
eligibility still rejects an unconsented channel (`delivery/policy.go:16`).

**Fix direction:** make this explicit requirement part of the reviewed plan and
scenario suite, then include the early gate in that generated draft. Other
journeys may intentionally wait for opt-in, so do not impose this behavior
universally on every workflow.

### P2 — Provider usage and attempt metadata are discarded

`Provider.Generate` returns only bytes (`ai/providers.go:21`). OpenAI response
decoding (`:90`) keeps status/output but not usage or actual response model;
it returns only text (`:112`). Claude likewise retains stop reason/content,
not usage. The Composer may call a provider twice (`ai/composer.go:117`), while
`Proposal` (`:39`) exposes neither usage nor attempt totals.

**Impact:** actual input/output/reasoning consumption and costs cannot be reported
for the live smoke. Retrospective content counting cannot recover hidden
reasoning, raw output formatting or an earlier repair attempt. This accounting
gap did not cause the six behavior failures, but prevents accurate measurement.

**Fix direction:** return structured provider results with sanitized usage,
actual model, request/attempt identifiers and timing. Aggregate all attempts,
including invalid/repaired candidates. Represent unavailable usage as unknown,
not zero. Contract-test both providers with mocked responses; do not store keys,
raw customer data or private reasoning.

## What the evidence does and does not show

- The same ten deterministic scenarios still reproduce 4/10 generated versus
  10/10 canonical passes; all isolation checks pass.
- Runtime and simulator share node decisions; both map custom exit reasons the
  same way. Missing profile-check nodes cannot be repaired by execution speed.
- Profile-only changes are not purchase events. A global event exit is not a
  substitute for a profile condition where the brief requires both sources.
- There is no observed runtime crash, duplicate action, unauthorized send or
  workspace leak in this probe. This is not a proof those can never happen.
- Structural validation and existing green tests are useful; they do not establish
  arbitrary AI brief compliance. One recorded proposal is not a model success rate.

## Recommended correction order

1. Strengthen required-scenario publication readiness so known unmet criteria
   cannot be presented as ready.
2. Specify canonical AI outcome codes and remove ambiguous prompt vocabulary.
3. Add a reviewed behavior contract and deterministic cases for first/final
   profile checks and immediate no-channel exit; show unmet criteria at review.
4. Capture provider usage and per-attempt metadata.
5. Re-run the frozen ten cases before requesting another live generation. Keep
   generation and publishing separate human-approved actions.

Only the audit document/evidence are added here. No corrective implementation,
provider call, migration, new execution service or language rewrite is included.
